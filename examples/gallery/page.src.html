Slat Gallery

Twenty plots built from slats. The first three rebuild v1's demos; the rest are magazine-style pieces, each designed around its data. Each slat owns its CSS and its layout, and a chart takes its colors from a theme object, so a slat looks the same in any app. Every chart switches between horizontal and vertical, and between the CSS version and the JS version of animation.

Same look in any app

A slat is meant to be shared, so it has to look and lay out the same in every app that uses it. Three rules give that: the slat owns its CSS and its sizes, the app hands rhp colors and a font as a theme object, and no page stylesheet reaches inside a chart. Charts stay plain DOM (no shadow root), so everything a developer does with DOM still works.

What the app gives
A theme object with fixed keys: series (a list), positive, negative, ink, muted, grid, surface, low, high, font. Pass it once with <Theme value={…}> around the app, or per chart with theme. Missing keys fall back to rhp's defaults. It is written inline on the chart root as --rhp-<key> (15 custom properties with 6 series colors); switching theme rewrites those and nothing else. This page switches light and dark that way.
What a slat owns
css: applies to that slat type's slats only, the slat root included, never to the page or to another slat type. band: px per slat along the stack. inset: the empty share of the band beside a Bar. room: px its labels need outside the plot at each end. The Chart pads each side to the largest room its Plots ask for, and the axis's. Color props take a theme key ("series-3", "positive") or any CSS color.
Why a page can't change a chart
Every declaration rhp or a slat makes is !important inside @layer rhp.place, rhp.slat, rhp.core, declared first in <head>. For !important the first-declared layer wins, and a layered one beats an unlayered one, so no page rule wins, whatever its specificity, order or own !important. A zero-specificity guard sets box, text and paint properties on rhp's elements and slat roots, and the chart body inherits nothing from the page.
What the page still controls
The chart root's box: width, margin, display, background, border, everything but its padding (the gutters). On any element: opacity, cursor, filter and transform, which rhp leaves alone. On elements a slat author adds (an icon <span>), any property the slat's CSS doesn't set. A --rhp-* variable set on rhp's own elements, and inline !important, which a page only writes on purpose. (Page --rhp-* variables on :root, as v1 advised, no longer reach inside.)
What developers keep
document.querySelector, Testing Library queries, page-level click listeners, app classes for properties rhp doesn't set (opacity-50 works; bg-red-500 on a Bar doesn't, use color), text search, and Solid hydration. A shadow root per chart lost all of these.
Injection
One constructable stylesheet for the core and one per slat type with css, made once and adopted by every document that shows a chart (an iframe's or a popup's too, and a shadow root the app made). A <style> element where constructable sheets are missing (jsdom, older browsers). Slat CSS is scoped by rewriting each selector S to .scope:is(S), .scope :is(S), with the scope named from a hash of the CSS, so server and browser agree.

How d works

d is the object a slat function receives. It is one Proxy per slat, made when the slat is made, and it stores no values. Reading d.value reads the Plot's value data group (through one memo per group) and returns item row of it, where row is the slat's row number.

Does it copy or write data?
No. There is no per-slat object of values and no store write. The only per-slat state the Plot keeps is the slat's position.
How many signals does it add?
Per Plot: one memo per data group, plus the count, the ids and the positions. Per slat: nothing for list groups; one memo for each computed group that slat reads; one effect that writes --rhp-position. Each block adds one effect for its CSS variables.
What re-runs when data changes?
The expressions that read the changed group. A plain array replaced: every slat's expressions that read it re-run, and only changed values are written. A store list (value={store.values}) with one item set: only that slat's expressions re-run.
Measured cost
1,000 slats, each one Bar reading d.value; one value changed. Plain array replaced: 1,000 re-runs, 1 style write, 3 to 8 ms. Store item set: 1 re-run, 1 style write, 0.4 to 0.6 ms. Creating two such Plots (2,000 slats) took 60 ms. Headless Chromium, three runs.
Side effects
Destructuring (({ value }) =>) reads once and never updates, as with Solid props. A slat's root style must be an object, because a string replaces the whole attribute and wipes --rhp-position.

What a data group can be

Any prop of a Plot that is not a setting is a data group. You add data by adding a prop.

CSS variables a slat may set

In its own css: --rhp-label-size, --rhp-radius, --rhp-tick-width, --rhp-cell-gap, --rhp-length-time, --rhp-length-ease, --rhp-slide-time, --rhp-slide-ease. rhp writes the rest (the theme, --rhp-min, --rhp-max, the gutters, each block's numbers). Every variable is --rhp- prefixed, so an app's own variables never collide.
